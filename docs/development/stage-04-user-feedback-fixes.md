# ReadMD 阶段 04：真机反馈修复记录

日期：2026-05-24
最近更新：2026-06-07

## 1. 阶段背景

阶段 04 的核心任务不是继续堆功能，而是围绕用户在真机上的连续反馈，集中修复“能不能稳定打开、能不能顺手阅读、能不能安心编辑保存”这三件事。

这一阶段的特点是：

- 问题并非集中在单一模块，而是同时出现在文件读取、Markdown 预览、草稿恢复、主题配色、阅读布局和返回逻辑上。
- 很多问题只有在真机上才能稳定复现，尤其是 Android 10/12、输入法弹出、大字模式、夜间模式和长 Markdown 文档阅读场景。
- 交互方案在阶段中途发生过一次明显调整：早期曾尝试“打开后直接进入可编辑状态”，后来根据阅读优先原型和真机反馈，改为“打开后默认进入阅读页，点击进入编辑模式；保存或另存后自动回阅读页”。

## 2. 反馈来源与问题演进

### 第一轮反馈：基础可用性问题

首轮真机反馈主要集中在“能不能稳定使用”：

1. 大字模式下按钮文字会挤在一起，典型场景是“关闭大字”按钮。
2. “字体”“行距”滑动条调节后，界面文字和间距没有明显变化。
3. 打开文件后还需要再点“编辑”，不够像备忘录。
4. 导入文件、点击阅读、打开 Markdown 文件时仍可能闪退。

### 第二轮反馈：闪退与预览链路问题

在 Android 10/12 真机上，问题进一步收敛到文档读取和预览链路：

1. Obsidian 可正常打开的测试 Markdown，在 ReadMD 中无法正确渲染，浏览几秒后闪退。
2. 点击“新建”后会直接闪退，重新进入应用后还可能再次闪退。
3. 自动恢复的旧草稿可能把应用带回闪退循环。

### 第三轮反馈：阅读体验与主题问题

当闪退问题初步缓解后，新的问题集中暴露在阅读体验上：

1. 夜间模式下部分区域出现黑底黑字，可读性差。
2. 预览区域偏小，不适合作为主阅读区。
3. 点击编辑后输入法占用大量屏幕空间，编辑区剩余空间太小。
4. 缺少明确的日间/夜间切换入口，大字模式也没有和夜间模式解耦。

### 第四轮反馈：交互细节问题

在基础链路基本打通后，反馈开始集中在细节交互：

1. 希望阅读页支持双指缩放字号。
2. 打开文件后底部“已打开...”提示影响阅读。
3. 缺少系统返回手势/返回键的上一界面逻辑。
4. 编辑后保存或另存，希望自动回到阅读页。

### 第五轮反馈：阅读页性能与手势问题

2026-05-25 的最新反馈指出：

1. 阅读页单指滑动浏览长 Markdown 文档时卡顿明显。
2. 双指缩放功能虽然代码中已接入，但真机上几乎感觉不到效果。

这一轮反馈说明问题已经从“有没有功能”转向“功能是否真正可用”。

### 第六轮反馈：缩放影响范围与滚动回归

2026-05-26 的反馈进一步指出：

1. 阅读页双指缩放会影响首页字号，导致返回首页后列表和按钮也被放大。
2. 放大到约 160% 时，部分较大的 Markdown 标题或文字会出现重叠，阅读区显得混乱。
3. 最新版阅读页可以缩放，但又出现无法上下滑动阅读全文的问题。

这说明阅读缩放需要从“全局字号设置”中拆出来，变成阅读页自己的临时阅读参数；同时手势识别不能拦截单指滚动。

## 3. 问题定位与分析

### 3.1 文件打开与闪退

阶段 04 前半段的闪退，主要来自三类风险叠加：

- 文件内容里存在 BOM、空字符、异常换行或历史脏字符。
- 草稿恢复逻辑过早介入，把异常内容反复恢复进当前会话。
- Markdown 预览链路不够稳，复杂内容在真机上容易触发 UI 压力或异常。

处理方向不是单点修补，而是把“文件读取 -> 内容清洗 -> 草稿恢复 -> 预览渲染”整条链路逐步收紧。

### 3.2 夜间模式与大字模式

问题根源不只是颜色没改，而是主题状态没有被完整传导到所有阅读相关组件，包括：

- 首页卡片和说明文字
- 阅读页预览容器
- 编辑页输入区
- Markdown 预览控件内部前景色和链接色

同时，大字模式此前更多只作用于部分正文，没有覆盖按钮高度、触控面积和设置项字号。

### 3.3 阅读页卡顿与双指缩放不明显

这一轮定位出来的核心原因有两个：

1. 阅读页此前把 `detectTransformGestures` 挂在外层 Compose 卡片上，内部真正显示 Markdown 的却是 `AndroidView` 承载的原生 `TextView`。两层触摸处理容易互相争抢，导致单指滚动发黏，而双指缩放也很难稳定命中。
2. 预览控件在 `update` 时会重复执行 `markwon.setMarkdown(...)`。这意味着哪怕只是字号变化、主题变化或轻微重组，也可能触发整段 Markdown 再次解析和重绘，长文档场景下很容易出现阅读卡顿。

这类问题不是“再调大缩放倍率”能解决的，必须把手势和渲染更新路径一起改掉。

### 3.4 阅读缩放影响首页

阅读页手势缩放最初复用了全局 `fontScale`。这样实现简单，但副作用很明显：用户为了读清当前文档临时放大字号，首页、最近文件列表、设置面板等非阅读区域也会被同步放大，容易造成布局拥挤。

产品定位上，首页承担的是“找文件”和“进入文档”，不应该被某篇文档的临时阅读习惯影响。因此阅读页手势缩放应当只影响当前阅读预览。

### 3.5 放大上限与文字重叠

真机反馈显示，约 160% 时较大标题容易出现重叠。结合移动端阅读场景，阶段 04 将最大阅读缩放收敛到 155%：

- 155% 比 150% 多一点阅读余量。
- 155% 避开了用户已经观察到的 160% 混乱区间。
- 大字模式仍可通过独立开关提供整体适老化体验，不需要把普通手势缩放推得过高。

## 4. 主要修复动作

### 4.1 文件与草稿链路

1. 文件读取增加编码识别、BOM 清理、空字符与异常换行清洗。
2. 草稿恢复只针对真实发生过编辑变更的内容，减少旧草稿把应用拖回闪退循环。
3. 新建备忘录不再过早写入会被强制恢复的初始草稿。

### 4.2 Markdown 预览链路

1. 预览能力切换到成熟的 Android Markdown 渲染方案。
2. 阅读页和编辑页解耦，避免同屏同时承载大编辑框和完整预览。
3. 预览内容增加安全清洗和超长内容截断说明，降低超长文档的瞬时压力。

### 4.3 阅读与编辑页面结构

1. 文档页拆分为“阅读页”和“编辑页”两种状态。
2. 打开文件后优先进入阅读页，把主要空间留给 Markdown 预览。
3. 编辑页去掉同屏预览，保留保存、另存、导出工具栏，把主要高度交给输入框。
4. 保存或另存成功后自动返回阅读页，便于立即检查渲染效果。

### 4.4 主题、字号与适老化

1. 引入独立的 `darkMode` 设置并持久化。
2. 将主题拆分为日间、夜间、大字日间、大字夜间四种组合。
3. 字体和行距滑动条绑定到首页、阅读页、编辑页、设置页、按钮和最近文件列表。
4. 按钮高度随字号和文字长度自动增长，避免大字模式下文字叠在一起。

### 4.5 交互细节

1. 打开文件成功后不再弹出“已打开...”底部提示，只在失败、保存、导出等需要反馈的动作中保留提示。
2. 接入系统返回手势/返回键逻辑：设置面板优先关闭，编辑页返回阅读页，阅读页返回首页。
3. 设置面板新增“大字模式”和“夜间模式/日间模式”两个独立切换按钮。

### 4.6 本轮新增：阅读页滚动与双指缩放修复

2026-05-25 针对阅读页卡顿和双指缩放不明显，追加了以下处理：

1. 移除阅读页外层 Compose 卡片上的缩放手势监听，避免与内部原生预览控件争抢单指滚动事件。
2. 将双指缩放手势下沉到 Markdown 预览内部的原生 `TextView`，使用原生缩放检测器处理双指手势。
3. 预览控件改为“内容变化时才重新执行 Markdown 渲染”，仅字号、行距、主题变化时不再重复整段解析。
4. 阅读页增加当前阅读字号百分比提示，让双指缩放是否生效可以被直接观察到。

这一轮修复的目标不是增加新功能，而是把“能滚得动、缩得出来、缩放后看得见变化”这三个体验问题一次收紧。

### 4.7 本轮补充：阅读缩放隔离与滚动修复

2026-05-26 追加处理：

1. 新增阅读页独立缩放状态，双指缩放只改变当前阅读预览，不再写入全局字体设置。
2. 全局字体滑动条和阅读手势缩放的最大值统一收敛到 155%，减少大标题和大字模式组合时的重叠风险。
3. Markdown 预览在大字号时强制保留更安全的最小行距，降低文字上下挤压。
4. 修复原生缩放检测器吞掉单指触摸事件的问题，让单指上下滑动重新交给 `TextView` 处理。

### 4.8 本轮补充：常用 LaTeX 数学公式预览

2026-05-26 追加处理：

1. 当前项目此前不支持 MathJax，也没有任何数学公式渲染依赖；Markdown 预览只覆盖标题、列表、代码块、表格等常见 Markdown 元素。
2. 经过调研，Markwon 官方提供 `ext-latex` 扩展，可在现有原生 `TextView` Markdown 预览链路中渲染 LaTeX 内容；相比引入 WebView + MathJax，这条路线改动更小，也更符合当前“本地、轻量、阅读优先”的产品定位。
3. 新增 `markwon-inline-parser` 和 `markwon-ext-latex` 依赖，并在 `MarkdownPreview` 中接入 `MarkwonInlineParserPlugin` 与 `JLatexMathPlugin`。
4. 已启用行内公式解析。当前推荐写法为 `$$E = mc^2$$`；块级公式可使用独立 `$$` 包裹。
5. 为避免破坏前面已经修复的长文档滚动性能，预览控件仍然默认只在 Markdown 内容变化时完整重渲染；仅当文档包含 LaTeX 公式并且字号跨过约 5% 的缩放档位时，才重渲染公式，让公式大小可以跟随阅读缩放，同时避免每一次微小手势变化都触发整文解析。

当前约束：

- 这里实现的是 Markwon LaTeX 公式渲染，不是完整浏览器 MathJax 引擎。
- 不引入网络资源，不依赖在线服务。
- 复杂宏包、特殊 MathJax 扩展和 Obsidian 插件语法不承诺完整兼容。

### 4.9 本轮补充：保存写回与文件类型入口收紧

2026-06-07 追加处理：

#### 问题 A：保存行为像“另存”

用户现象：

- 在编辑已有文件后点击“保存”，应用会弹出系统文件管理器。
- 从用户理解看，“保存”应该修改当前正在编辑的原文件；弹出文件管理器会让用户误以为应用正在创建新文件，或者原文件没有被更新。
- 这个问题会直接影响用户对应用可靠性的判断，因为备忘录类应用最核心的信任点就是“我改了内容，点保存，原文件确实被改掉”。

根因分析：

- `saveCurrentFile()` 原本已经包含“写回当前 URI”的分支，并不是完全缺少保存原文件能力。
- 触发误跳转的关键在于 `canWriteCurrentFile` 判断偏保守：它主要依赖 `ContentResolver.persistedUriPermissions` 中是否存在持久化写权限。
- Android 系统文件选择器和不同文件提供方的行为并不总是一致。有的提供方会返回本次会话的写授权，但持久化写权限可能失败或只持久化读权限。
- 一旦应用把“持久化写权限失败”理解成“当前文件绝对不可写”，就会提前进入 `requestSaveAs()`，用户看到的就是“保存也打开文件管理器”。

解决方案：

1. `openPickedDocument()` 在打开文件时保留本次文件选择器返回的写授权信息。如果本次授权中包含 `FLAG_GRANT_WRITE_URI_PERMISSION`，当前会话内允许直接尝试保存。
2. `DocumentRepository.persistUriPermission()` 先尝试持久化组合权限，再分别尝试持久化读权限和写权限，降低组合授权失败后读写权限都没有落下的风险。
3. `DocumentRepository.canWrite()` 不再只看持久化权限，也会查询文档提供方的 `DocumentsContract.Document.FLAG_SUPPORTS_WRITE`，作为判断文件是否支持写入的补充依据。
4. “保存”的产品规则被重新固定：有当前文件 URI 且判断可写时，直接调用 `writeText(uri, content)` 写回原文件；只有没有当前 URI、当前文件不可写或写入失败时，才提示用户另存。
5. 保存失败时不清空草稿、不覆盖状态，只显示失败提示，用户仍可继续编辑或手动选择“另存”。

设计取舍：

- 没有把“保存失败后自动弹出另存”作为默认行为，因为自动弹出会再次模糊“保存”和“另存”的边界。
- 当前策略是：保存优先写原文件；失败时明确提示；用户主动点“另存”才创建副本。
- 这样更符合备忘录软件的直觉，也能避免用户在不知情的情况下生成多个副本。

#### 问题 B：非 Markdown 文件是否应该拒绝打开

用户现象：

- 系统文件选择器可能展示范围较宽，用户有机会选到 PDF、图片、压缩包或其他非文本文件。
- 如果这类文件进入读取链路，轻则出现乱码，重则给 Markdown 渲染、文本解码和预览控件带来异常压力。
- 早期为了兼容某些文件管理器对 `.md` 的 MIME 标注不准确，入口 MIME 类型放得较宽，这有利于找到 `.md`，但也增加了误选其他文件的概率。

根因分析：

- Android 文件选择器通常以 MIME 类型筛选文件，但不同文件管理器对 `.md` 的 MIME 识别并不稳定。
- 某些 `.md` 文件可能被标为 `text/plain`，甚至 `application/octet-stream`；如果入口只允许 `text/markdown`，用户可能找不到自己的 Markdown 文件。
- 但如果完全相信宽泛 MIME 类型，又可能把非笔记文件送入文本读取链路。
- 因此需要在“文件选择器入口尽量能看到目标文件”和“应用读取前严格校验文件类型”之间做二次防线。

解决方案：

1. 新增 `SupportedFileTypes.kt`，集中管理 ReadMD 支持的文件类型。
2. 读取前根据展示文件名做扩展名校验，只允许 `.md`、`.markdown`、`.txt`。
3. 对没有扩展名但 MIME 为 `text/markdown` 或 `text/x-markdown` 的文档保留兼容，避免极少数无扩展名 Markdown 文档被误拒绝。
4. `.pdf`、`.png`、`.zip` 等带有明确非支持扩展名的文件会在真正读取前被拒绝，错误提示为“当前仅支持打开 .md、.markdown 或 .txt 文件”。
5. 文件选择器仍保留较宽 MIME 类型，以尽量让不同 Android 文件管理器中的 `.md` 文件可见；真正的安全边界放在应用读取前的二次校验。

设计取舍：

- TXT 文件继续支持。原因是 TXT 是纯文本，适合作为轻量备忘录格式，也常见于 AI 回复、临时记录、会议纪要等场景。
- TXT 的支持不意味着 ReadMD 要扩展为通用文件阅读器。Word、PDF、图片、HTML、JSON、日志、压缩包等仍不进入当前阶段。
- 对 `.txt` 的预览按纯文本/Markdown 兼容方式显示；如果内容里刚好有 Markdown 标记，可以被基础渲染，但产品上仍把它视为普通文本笔记。

当前约束：

- “保存”不负责创建副本；创建副本使用“另存”。
- `.txt` 支持只代表纯文本读写，不代表把所有非 Markdown 格式都作为笔记格式支持。
- 入口拦截不能替代写入失败处理，保存失败时仍必须保留用户输入并提示另存。
- 后续如果增加 PDF、图片或其他格式，也应该走独立功能设计，不应直接放宽当前 Markdown/TXT 读取入口。

### 4.10 本轮补充：边缘情况、容量上限与轻量化

2026-06-07 追加处理：

#### 问题 A：单个 Markdown 文件过大

用户关注点：

- 如果用户选择一个明显大于普通备忘录的 Markdown 文件，应用是否会卡死、闪退或导致编辑体验不可用。
- 用户给出的 100KB 是一个参考值，但 ReadMD 也需要兼容较长的 AI 回复、学习笔记、会议纪要和技术文档，因此不能把上限设得过低。

现状分析：

- 早期代码把 `MAX_OPEN_BYTES` 和读取兜底限制设置为 8MB。
- 8MB 对桌面文本编辑器不算夸张，但对手机端 Compose 编辑框、Markwon 渲染和草稿持久化来说偏激进。
- 当前阅读页虽然会把 Markdown 预览截断到 `MAX_PREVIEW_CHARS = 120_000` 字符，但完整内容仍会进入应用状态和编辑框；文件越大，越容易影响输入法弹出、编辑滑动、草稿保存和系统内存。

解决方案：

1. 将单个文件打开上限从 8MB 收紧到 2MB。
2. 保留 120000 字符的预览截断策略，避免长文档一次性全部交给 Markdown 预览控件。
3. 文件大小已知时，在读取前拦截；文件大小未知时，`readAllBytesLimited()` 在实际读取过程中继续按 2MB 兜底拦截。
4. 超限提示改为“文件超过 2MB，建议拆分后再打开”，让用户知道不是文件损坏，而是当前版本主动保护阅读和编辑体验。

设计取舍：

- 2MB 大约已经显著超过普通手机备忘录和多数 AI 生成 Markdown 的长度，日常使用足够宽松。
- 继续允许 8MB 会增加真机卡顿和闪退风险；收紧到 100KB 又可能误伤稍长的学习笔记。
- 因此当前阶段选择 2MB 作为“轻量备忘录 App”的合理硬上限。后续如果要支持更大文档，应改为分页、分块读取或虚拟列表渲染，而不是简单调大上限。

#### 问题 B：最近笔记最多显示多少条

用户关注点：

- “最近笔记”模块应该能覆盖常用文件，但不能无限增长，否则首页扫描成本、SharedPreferences 存储和列表可读性都会变差。

现状分析：

- 早期实现中最近文件列表最多保留 10 条。
- 10 条比较克制，但对频繁测试、学习笔记和多文件备忘场景略少。
- 每条最近记录只保存 URI、展示名、打开时间、可写状态和约 160 字符摘要，不复制完整文件，因此适度增加数量不会显著增加存储压力。

解决方案：

1. 新增 `MAX_RECENT_FILES = 20`，最近文件列表最多保留 20 条。
2. 每次打开文件时，把当前文件移动到列表顶部，并去重。
3. 超出 20 条后只保留最近打开的 20 条。

设计取舍：

- 20 条足够覆盖常用文件，又不会让首页变成笨重的文件管理器。
- 最近文件不是完整文件库；ReadMD 仍然不主动扫描手机存储。
- 如果未来需要更多文件管理能力，应做独立“本地笔记列表/目录选择”功能，而不是无限放大最近记录。

#### 问题 C：其它影响安全和稳定的边缘情况

本轮结合 code review、testing setup、technical debt 和本地文件威胁建模思路，重新检查了以下边界：

1. 文件类型边界：只允许 `.md`、`.markdown`、`.txt`，避免 PDF、图片、压缩包等二进制内容进入文本解码和 Markdown 渲染链路。
2. 文件大小边界：已知大小和未知大小都按 2MB 拦截，避免文件提供方不返回大小时绕过保护。
3. 预览渲染边界：预览最多渲染前 120000 字符，完整内容仍可在编辑区查看和保存。
4. 最近文件边界：最近记录只保存元数据和短摘要，不保存完整文件内容。
5. 权限边界：保存优先写回当前 URI，但写失败时保留草稿和用户输入，不静默丢失内容。
6. 草稿边界：草稿恢复只处理真实未保存编辑，避免新建初始内容造成恢复循环。
7. 主题和字号边界：阅读缩放上限保持 155%，避免大标题和大字模式组合时文字重叠。

当前仍需注意：

- 超大文件支持还不是“真正的大文档阅读器”能力；当前只是通过上限和截断保护稳定性。
- 复杂 Markdown、公式和表格仍可能比普通文本消耗更多渲染资源，真机测试时应继续保留长文档样例。
- SharedPreferences 适合当前小规模最近文件和设置存储；如果未来要保存大量笔记索引，应迁移到 Room 或其他结构化存储。

#### 问题 D：APK 轻量化

用户关注点：

- 当前测试包约 19.2MB，作为轻量备忘录 App 看起来偏大，希望在不影响功能的前提下降低体积。

现状分析：

- 该体积来自 Debug APK。Debug APK 包含调试构建特征，不能代表正式发布体积。
- 项目中声明了 `androidx.material:material-icons-extended`，但当前代码没有使用任何 Material Extended Icons。
- Release 构建此前没有显式启用 R8 代码压缩和资源压缩。

解决方案：

1. 移除未使用的 `androidx.material.icons.extended` 依赖。
2. 新增 release 构建配置，启用 `isMinifyEnabled = true` 和 `isShrinkResources = true`。
3. 新增 `app/proguard-rules.pro`，为未来依赖保留项目级 R8 规则入口。
4. 保留 Compose Preview 所需的 `ui-tooling-preview` 和 debug tooling，不影响 Android Studio 预览和开发体验。

验证结果：

- 优化后 Debug APK：`app/build/outputs/apk/debug/app-debug.apk`，约 12.36MB。
- 未签名 Release APK：`app/build/outputs/apk/release/app-release-unsigned.apk`，约 1.89MB。
- Release APK 尚未正式签名，不能直接作为公开发布包；但它能说明启用压缩后的正式包体积潜力。

设计取舍：

- 没有为了进一步压缩体积而移除 Markdown 表格、任务列表、LaTeX 等已实现功能。
- 没有移除 Compose Preview 相关开发依赖，因为它们对后续界面调试仍有价值。
- 后续正式发布时，应优先发布签名 Release APK 或 AAB，而不是继续把 Debug APK 当作主要体验包。

#### 本轮 skill 情况

- 外部 skill 安装通道在重试后恢复。
- 已安装 `security-best-practices` 和 `security-threat-model`。
- `security-best-practices` 当前主要覆盖 Web 语言，没有直接的 Kotlin/Android 参考文档；本轮未强行套用不匹配的规则。
- `security-threat-model` 的方法论用于检查 ReadMD 的文件 URI、权限、文件类型、大小限制和本地草稿边界。

### 4.11 本轮补充：长文档快速定位与阅读到编辑位置同步

2026-06-08 追加处理：

#### 问题：长文档只能匀速滑动，难以快速到达中段或末尾

用户现象：

- 当单个 Markdown 文档内容较多时，用户想直接查看文档中部、倒数几段或末尾内容。
- 早期阅读页和编辑页主要依赖系统默认滚动，虽然稳定，但长文档场景下需要反复滑动，效率较低。
- 如果用户在阅读页看到某一段想修改，点击“进入编辑模式”后，编辑页从默认位置开始显示，用户还要再次寻找同一段内容。

根因分析：

- 阅读页使用原生 `TextView` 承载 Markwon 渲染内容，滚动位置此前没有暴露给 Compose 状态。
- 编辑页使用 `OutlinedTextField` 展示 Markdown 源码，阅读页的渲染位置和源码字符位置并不存在天然的一一对应关系。
- 直接在编辑页增加完整进度滑块会带来输入法遮挡、光标移动、文本选择冲突和界面复杂度增加等问题。

解决方案：

1. 在 `MarkdownPreview` 内部的 `ZoomableMarkdownTextView` 中计算当前垂直滚动比例。
2. 阅读页右侧新增覆盖式细定位条，平时以浅灰色细条显示，不占用正文布局空间，也不显示具体百分比。
3. `DocumentState` 新增 `readingScrollFraction`，用于记录阅读页当前滚动比例。
4. 点击“进入编辑模式”时，ViewModel 把当前 `readingScrollFraction` 写入 `pendingEditScrollFraction`。
5. 编辑页打开后，根据该比例估算 Markdown 源码中的字符位置，并把编辑框光标移动到对应段落开头附近。
6. 编辑定位完成后清空 pending 状态，避免后续普通编辑反复跳转。
7. 右侧定位条采用“长按后再拖动”的方式触发快速定位：默认状态足够细，不干扰阅读；长按激活后临时加粗，便于手指操作。

设计取舍：

- 当前同步是“近似位置同步”，不是精确行号同步。Markdown 预览高度会受到标题、表格、公式、列表缩进等影响，因此阅读 70% 不一定等于源码字符 70% 的精确位置。
- 近似同步已经能解决“从头重新找”的主要痛点，同时实现风险远低于渲染位置到源码行号的精确映射。
- 暂不在编辑页增加独立进度滑块。编辑页的首要任务是稳定输入，过多拖动控件容易和输入法、光标、选区拖拽互相干扰。
- 如果未来需要更精确的长文档导航，应优先考虑 Markdown 标题目录/大纲定位，而不是继续增加编辑页手势复杂度。

当前约束：

- 阅读页右侧定位条只影响当前阅读预览滚动，不改变全局字号、最近文件列表或编辑内容。
- 定位条应保持覆盖式、细线化设计，不要为了显示百分比或控制面板挤占 Markdown 正文宽度。
- 从阅读页进入编辑页时，只做一次近似定位。
- 编辑页定位通过移动光标实现，不强行接管 `OutlinedTextField` 内部滚动状态。
- 单指滚动和双指缩放仍然保持此前修复后的职责边界。

## 9. 修复冲突与防回归清单

阶段 04 的多个修复点彼此有关联，后续继续开发时需要特别避免“修 A 又破坏 B”。

### 9.1 阅读缩放与首页布局

历史问题：

- 阅读页双指缩放最初复用了全局 `fontScale`，导致返回首页后首页按钮、搜索框和最近文件列表也被放大。

当前约束：

- 阅读页双指缩放只能修改当前阅读预览的局部缩放状态。
- 全局字体滑动条仍然可以调整首页、编辑页、设置页等整体字号。
- 不要把阅读手势缩放重新接回全局 `settings.fontScale`。

回归检查：

- 在阅读页放大到 155% 后返回首页，首页布局应保持原本大小。
- 再进入同一文档，阅读页可以继续按当前会话的阅读缩放显示。

### 9.2 手势缩放与单指滚动

历史问题：

- 外层 Compose 手势监听和内部原生 `TextView` 滚动互相争抢，导致单指滚动卡顿。
- 后续改为原生缩放检测后，缩放检测器又一度吞掉单指触摸事件，导致无法上下滑动阅读全文。

当前约束：

- 双指手势由 Markdown 预览内部处理。
- 单指触摸必须交还给原生 `TextView` 滚动。
- 不要在阅读卡片外层重新挂 `detectTransformGestures` 或会消费全部触摸事件的 `pointerInput`。

回归检查：

- 单指上下滑动长文档应稳定。
- 双指缩放时字号百分比应变化。
- 单指滚动和双指缩放不能互相破坏。

### 9.3 Markdown 渲染性能与内容更新

历史问题：

- 预览控件在样式变化时重复执行完整 `markwon.setMarkdown(...)`，长文档会出现卡顿。

当前约束：

- 只有 Markdown 内容变化时才重新执行完整渲染。
- 字号、行距、颜色变化只更新视图样式。
- 如果未来加入本地图片、代码高亮或链接点击，也要注意不要让每次滑动或缩放触发整文重渲染。

回归检查：

- 打开长文档后，单指滚动不应明显掉帧。
- 调整字号或夜间模式时，内容不应丢失或闪退。
- 编辑后回到阅读页，更新后的 Markdown 必须重新渲染。

### 9.4 字号上限与大字模式

历史问题：

- 放大到约 160% 时，较大的标题和部分文字会重叠。
- 大字模式如果只放大正文、不放大按钮和间距，会出现按钮文字挤压。

当前约束：

- 阅读缩放和全局字体上限都控制在 155%。
- 大字模式仍然作为独立开关处理整体适老化，不依赖普通缩放继续往上堆。
- 大字号下 Markdown 预览需要保留更安全的最小行距。

回归检查：

- 普通模式 155% 下，大标题不应明显上下重叠。
- 大字模式下按钮文字不能叠在一起。
- 大字模式和夜间模式组合时仍应可读。

### 9.5 草稿恢复与新建文件

历史问题：

- 新建文件后过早写入草稿，闪退重启后可能反复恢复异常草稿，造成循环闪退。

当前约束：

- 草稿恢复只处理真实编辑过且未保存的内容。
- 新建备忘录可以进入编辑页，但不能把无意义初始内容当成必须恢复的异常草稿。
- 文件内容进入状态前仍要做文本清洗，避免旧草稿或异常编码污染预览。

回归检查：

- 新建后不保存直接退出，再次进入不应闪退。
- 编辑真实内容后异常退出，应能恢复草稿。
- 保存成功后草稿应清除。

### 9.6 阅读优先与编辑便利

历史问题：

- 阶段中途曾尝试“打开后直接编辑”，后来又根据阅读优先原型改回“打开文件默认阅读页”。

当前约束：

- 打开已有文件默认进入阅读页。
- 新建备忘录默认进入编辑页，这是备忘录场景的合理例外。
- 保存或另存成功后自动回到阅读页。

回归检查：

- 导入已有 `.md` 后先看到阅读预览。
- 点击“进入编辑模式”后才能修改原文。
- 保存或另存后应回到阅读页。

### 9.7 提示反馈与阅读干扰

历史问题：

- 打开文件成功后底部弹出“已打开...”影响阅读。

当前约束：

- 成功打开文件不再显示底部 Snackbar。
- 保存、另存、导出、失败等需要确认或错误说明的动作仍保留提示。

回归检查：

- 打开文件后不应出现“已打开...”。
- 保存失败必须有明确提示，不能静默失败。

### 9.8 保存与另存边界

历史问题：

- 用户点击“保存”时进入系统文件管理器，看起来像“另存”，容易误以为应用不会修改原文件。
- 这个问题不是单纯的按钮文案问题，而是保存状态判断和 Android 文件授权模型之间的边界问题。
- 如果后续再次把 `canWriteCurrentFile` 简化为“只看持久化写权限”，同类问题可能重新出现。

当前约束：

- 保存优先写回当前原文件。
- 另存才打开系统文件管理器并创建新文件。
- 新建草稿第一次保存没有原文件 URI，可以进入系统另存流程。
- 当前文件无写权限或写入失败时，可以提示用户另存，但不能静默丢失草稿。
- 从系统文件选择器刚打开文件时，如果本次授权包含写权限，当前会话内应允许保存尝试。
- 持久化权限、文档提供方写标记、本次授权写标记应共同参与判断，不要只依赖其中一个信号。

实现注意：

- `saveCurrentFile()` 的分支要保持清晰：`currentUri == null` 或 `canWriteCurrentFile == false` 才请求另存；否则直接写当前 URI。
- `writeToUri()` 成功写回当前文件后，要同步更新 `content`、`draftContent`、`hasUnsavedChanges` 和最近文件摘要。
- 保存失败时只显示错误提示，不应清除草稿，也不应把未保存内容覆盖成旧内容。
- “保存后返回阅读页”的体验可以保留，但不能以丢掉用户正在编辑的内容为代价。

回归检查：

- 从文件选择器打开一个可写 `.md`，修改后点击“保存”，不应弹出文件管理器。
- 保存成功后再次打开原文件，应能看到修改后的内容。
- “另存”仍应打开文件管理器并生成副本。
- 新建备忘录第一次保存可以弹文件管理器，因为此时还没有原文件。
- 打开只读文件或第三方应用不允许写入的文件时，保存失败必须保留编辑内容，并允许用户再点“另存”。
- 从最近文件重新打开曾经可写的文件时，应尽量继续写回原 URI；如果权限已经丢失，应明确提示失败。

### 9.9 文件类型安全入口

历史问题：

- 文件选择器允许较宽的文本 MIME 类型，用户可能选择到非 Markdown/非纯文本文件，增加读取异常和预览异常风险。
- 早期为了让更多 `.md` 文件能在不同 Android 文件管理器里被看见，入口 MIME 类型不能收得太窄。
- 但是只依赖文件选择器筛选不够可靠，应用自身必须在真正读取文件前再判断一次。

当前约束：

- 只允许 `.md`、`.markdown`、`.txt` 进入读取链路。
- PDF、图片、压缩包、数据库等非文本笔记格式必须拒绝打开。
- TXT 作为纯文本备忘录格式保留支持，但不引申支持 Word、HTML、JSON 等其他格式。
- 带有明确不支持扩展名的文件，即使 MIME 类型看起来像文本，也应拒绝。
- 无扩展名但 MIME 明确为 Markdown 的文件可以兼容打开。

实现注意：

- 支持类型集中在 `SupportedFileTypes.kt` 管理，避免散落在 ViewModel、文件选择器和文档里各写一套规则。
- 文件选择器可以继续使用较宽 MIME 类型提高 `.md` 可见性，但 `openUri()` 读取前必须调用支持类型判断。
- 最近文件列表中的旧记录不能绕过类型判断；再次打开时仍要走同样校验。
- 不要为了支持 TXT 而放宽到“所有 text/* 都能打开”，否则日志、HTML、JSON 等文件会悄悄进入预览链路。

回归检查：

- `.md`、`.markdown`、`.txt` 应能打开。
- `.pdf`、`.png`、`.zip` 应被拒绝。
- 最近文件列表中的旧 URI 如果不再符合支持规则，也应在打开时被拒绝，而不是继续送入预览。
- 大小超过限制的支持格式文件仍应被文件大小保护拦截。
- 被拒绝的文件不应写入最近文件列表。
- 拒绝打开后，当前正在编辑的草稿不应被清空或替换。

### 9.10 大文件与预览边界

历史问题：

- 移动端 Markdown 预览、编辑框和草稿恢复都不适合无限制接收大文件。
- 早期 8MB 上限对手机备忘录场景偏大，容易把问题推迟到渲染或编辑阶段才暴露。

当前约束：

- 单个文件打开上限为 2MB。
- 文件大小已知时先检查元数据；文件大小未知时读取过程中继续按 2MB 兜底。
- Markdown 预览最多渲染前 120000 字符，超出部分通过提示说明。
- 不能为了“能打开更大文件”直接提高上限，除非同时引入分块读取、分页预览或虚拟化渲染。

回归检查：

- 100KB 左右的普通长笔记应能打开。
- 接近 2MB 的文件应能在构建层面被允许，真机上重点观察滚动和编辑体验。
- 超过 2MB 的文件应被拒绝，并显示清楚提示。
- 被拒绝的大文件不应写入最近记录，也不应覆盖当前草稿。

### 9.11 最近记录与本地存储边界

历史问题：

- 最近记录如果无限增长，会让首页变成弱文件管理器，也会增加 SharedPreferences 的长期存储压力。

当前约束：

- 最近笔记最多保留 20 条。
- 最近记录只保存 URI、展示名、时间、可写状态和短摘要，不保存完整文件内容。
- 清空最近记录只删除应用内记录，不删除用户真实文件。

回归检查：

- 连续打开 21 个不同支持格式文件后，列表应只保留最近 20 条。
- 重复打开同一个文件应移动到顶部，而不是产生重复记录。
- 清空最近记录后，用户本地文件不应被删除。

### 9.12 APK 轻量化与发布包边界

历史问题：

- Debug APK 约 19.2MB，作为轻量备忘录应用显得偏大。
- 未使用依赖和未启用 release shrink 会放大体积问题。

当前约束：

- 未使用的 `material-icons-extended` 不应重新加入，除非确实使用其中图标。
- Release 构建保持 `isMinifyEnabled = true` 和 `isShrinkResources = true`。
- Debug APK 主要用于开发测试，不作为正式体积判断依据。
- 正式分发应使用签名 Release APK 或 AAB。

回归检查：

- `.\gradlew.bat :app:testDebugUnitTest :app:assembleDebug` 应通过。
- `.\gradlew.bat :app:assembleRelease` 应通过。
- Debug APK 不应明显回到 19MB 级别，除非新增了明确必要的功能依赖。
- Release APK 应显著小于 Debug APK。

### 9.13 长文档快速定位与编辑同步

历史问题：

- 长文档只能依赖默认滚动，用户要到达中部或末尾需要反复滑动。
- 在阅读页看到某段内容后进入编辑模式，编辑页无法直接定位到相近源码位置。

当前约束：

- 阅读页可以通过右侧细定位条快速定位；默认应保持浅灰、细窄、低干扰。
- 定位条只在长按激活后临时加粗并允许拖动，不显示具体位置百分比。
- 阅读页滚动位置应记录为 `readingScrollFraction`，范围保持在 0 到 1。
- 进入编辑模式时，只把当前阅读比例作为一次性 `pendingEditScrollFraction` 使用。
- 编辑页不单独增加进度滑块，避免和输入法、光标、文本选择产生冲突。
- 编辑页定位是近似定位，不承诺 Markdown 渲染位置和源码行完全精确一致。

实现注意：

- `MarkdownPreview` 内部滚动回调不能吞掉单指滚动事件。
- 阅读定位条变化不应触发整篇 Markdown 反复重渲染。
- 右侧定位条应覆盖在阅读卡片内侧，不应改变当前预览框大小或压缩正文排版。
- 从阅读进入编辑后，应清空 pending 定位状态，避免用户继续编辑时被反复拉回旧位置。
- 光标定位应尽量落在段落或行开头附近，减少用户进入编辑后还要微调的距离。

回归检查：

- 单指滑动阅读仍应顺畅。
- 双指缩放仍应只改变阅读字号。
- 长按并拖动右侧定位条能跳到文档中部或末尾附近。
- 阅读页滚到 70% 附近后点击“进入编辑模式”，编辑框应定位到源码靠后位置。
- 编辑页正常输入、保存、另存、导出不应受 pending 定位状态影响。
